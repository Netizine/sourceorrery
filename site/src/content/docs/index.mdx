## From a credential to a reference

SourceOrrery is a local-first secrets platform written in Rust. Use the CLI to
manage credentials and a value-free project manifest to declare what your app
needs. Read them through an SDK, or inject them into a child process at launch.

<div class="so-feature-grid">
  <FeatureCard title="Encrypted local storage" icon="vault">
    Secret values are encrypted with XChaCha20-Poly1305 in a SQLite vault.
    Protect the vault key with your OS credential store, a passphrase, or both.
  </FeatureCard>
  <FeatureCard title="References in your repository" icon="link">
    Declare which secrets your project needs in its manifest.
    Inline `value` fields are rejected; keep names and other metadata free of secrets too.
  </FeatureCard>
  <FeatureCard title="Metadata by default" icon="shield-halved">
    Inspect names, versions and status without printing secret values.
    Revealing a value requires an explicit `get --reveal`.
  </FeatureCard>
  <FeatureCard title="A complete secret lifecycle" icon="clock-rotate-left">
    Version values, enforce activation and expiry, recover soft-deleted secrets,
    and inspect a tamper-evident audit log.
  </FeatureCard>
</div>

## Start with the CLI

[Install SourceOrrery](/getting-started/#install), then run these commands in
your project directory. The secret prompt is hidden; values are never command-line arguments.

```bash title="Create a development vault"
sourceorrery vault create development
sourceorrery secret set database-password --vault development
sourceorrery secret list --vault development
```

Declare the secret in a project manifest. The vault and secret name resolve to
`sourceorrery://development/database-password`:

```toml title="sourceorrery.toml"
[project]
name = "my-app"
vault = "development"

[secrets.database-password]
env = "DATABASE_PASSWORD"
```

```bash title="Check the manifest and launch your app"
sourceorrery check
sourceorrery run -- npm start
```

`npm start` receives `DATABASE_PASSWORD`; your parent shell is unchanged.
The child process can read and disclose its environment, so run code you trust.
The [getting started guide](/getting-started/) covers unlocking, verification
and working without an OS credential store.

## Use your language

All SDKs are read-only and share the Rust core's semantics. Manage vaults and
secret versions with the CLI, then read values through a scoped accessor in
your application.

## Know the security boundary

<Aside type="caution" title="Local protection, with clear limits">
SourceOrrery has not had an independent security audit and should not be
treated as a production secret store. Any process running with your
privileges that can unlock the vault can read it. The authenticated broker
and per-runtime access controls are planned, not available today.
</Aside>

| Protection | Available today |
| --- | --- |
| Secret values encrypted in the vault | Yes. Names, tags and other metadata remain visible. |
| References instead of credentials in project files | Yes, when you keep secret values out of names, comments and metadata. |
| Version policy and tamper-evident audit records | Yes. A full rollback of the vault needs an external checkpoint to detect. |
| Isolation from an agent running as your user | No. Local unlock access is the current boundary. |

Read the [threat model](/security/threat-model/) before choosing where to use
SourceOrrery. It distinguishes vault protection from secrets copied into
application memory, logs, process environments or other files.

## How it fits together

The CLI and SDKs use the same Rust implementation. A manifest stores
references, the local vault stores encrypted values, and the application
chooses when to resolve a secret.
