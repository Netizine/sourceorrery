SourceOrrery 0.1.4 is an encrypted local vault with a
cloud-secrets-manager-style lifecycle, a CLI with an interactive vault manager, and
read-only [SDKs](/sdks/) for Python, JavaScript/TypeScript, Rust, Java,
.NET, Go, C, C++ and PHP. It works on Windows, macOS and Linux.

<Aside type="caution" title="Use development credentials">
SourceOrrery has not been independently audited. Do not treat it as a
production secret store. Code that can unlock your vault can read its
secrets; the planned broker is not part of this release.
</Aside>

<Aside type="note" title="Documentation for 0.1.4">
This walkthrough targets **0.1.4**, including `.env` import and
`init --integration`. Check `sourceorrery --version` before following it.
The authenticated broker and remote providers remain on the [roadmap](/roadmap/).
</Aside>

## Install

There are three ways to install 0.1.4: the published packages, the files
on the GitHub release, or a build from source.

| Your starting point | Recommended route |
|---------------------|-------------------|
| Rust and a C compiler are already installed | [Install with Cargo](#from-the-package-registries) |
| You want a ready-to-run CLI without a compiler | [Download the release](#from-the-github-release) |
| You want to inspect or contribute to the implementation | [Build from source](#from-source) |

### From the package registries

The CLI is on crates.io, and Cargo builds and installs it in one step. You
need Rust 1.91.1 or newer and a C compiler for the bundled SQLite (on Linux
also `libdbus-1-dev` and `pkg-config` for the Secret Service);
[Building from source](/guides/building-from-source/#what-you-need) has
the commands to install them on each platform.

```bash
cargo install --locked sourceorrery-cli --version 0.1.4
```

`--locked` builds with the exact dependency versions the release was
tested with, from the lock file inside the crate; without it, Cargo picks
the newest compatible version of every dependency at install time.

The SDKs are published as packages for each language:

| Language | Package | Install |
|----------|---------|---------|
| Python | [`sourceorrery`](https://pypi.org/project/sourceorrery/) on PyPI | `pip install sourceorrery` |
| JavaScript / TypeScript | [`@sourceorreryai/sdk`](https://www.npmjs.com/package/@sourceorreryai/sdk) on npm | `npm install @sourceorreryai/sdk` |
| Rust | [`sourceorrery`](https://crates.io/crates/sourceorrery) on crates.io | `cargo add sourceorrery` |
| Java | [`ai.sourceorrery:sourceorrery`](https://central.sonatype.com/artifact/ai.sourceorrery/sourceorrery) on Maven Central | `<version>0.1.4</version>` (see [Java](/sdks/java/)) |
| .NET | [`SourceOrrery`](https://www.nuget.org/packages/SourceOrrery) on NuGet | `dotnet add package SourceOrrery` |
| Go | [`github.com/netizine/sourceorrery/bindings/go`](https://pkg.go.dev/github.com/netizine/sourceorrery/bindings/go) | `go get github.com/netizine/sourceorrery/bindings/go@v0.1.4` |
| PHP | [`sourceorrery/sourceorrery`](https://packagist.org/packages/sourceorrery/sourceorrery) on Packagist | `composer require sourceorrery/sourceorrery` |

Go, C, C++ and PHP load the C ABI library from the release (below); each
[SDK page](/sdks/) has the steps. How every package is published, and how
to check that what you installed is what was released, is in
[Supply chain](/security/supply-chain/).

### With a package manager

Each package manager downloads the CLI archive from the GitHub release
and checks its SHA-256 against the one recorded at release time, so what
it installs is the released file.

<Tabs syncKey="os">
<TabItem label="Windows">

```powershell
winget install Netizine.SourceOrrery
```

or, with [Scoop](https://scoop.sh):

```powershell
scoop bucket add sourceorrery https://github.com/Netizine/scoop-sourceorrery
scoop install sourceorrery
```

WinGet lists a new version once the community repository has merged its
submission, usually a few days after a release; the Scoop bucket has it at
once. The binaries are not code-signed yet, so SmartScreen may ask the
first time `sourceorrery` runs (*More info → Run anyway*); the hash check
above, the release's `SHA256SUMS` and `gh attestation verify` are how to
check a download in the meantime.

</TabItem>
<TabItem label="macOS">

```bash
brew install Netizine/sourceorrery/sourceorrery
```

</TabItem>
<TabItem label="Linux">

With [Homebrew on Linux](https://docs.brew.sh/Homebrew-on-Linux):

```bash

```

### From the GitHub release

The [v0.1.4 release](https://github.com/Netizine/sourceorrery/releases/tag/v0.1.4)
ships the CLI for Windows, macOS and Linux on x64 and arm64, the C ABI
library with its headers, and every SDK package (wheels, the npm tarballs,
the jar, the NuGet package), with a `SHA256SUMS` file to check each
download against.

<Tabs syncKey="os">
<TabItem label="Windows">

In PowerShell. On Windows on Arm, use `aarch64-pc-windows-msvc` in the
archive name instead of `x86_64-pc-windows-msvc`.

```powershell
$ErrorActionPreference = "Stop"
$release = "https://github.com/Netizine/sourceorrery/releases/download/v0.1.4"
$archive = "sourceorrery-0.1.4-x86_64-pc-windows-msvc.zip"
$dir = "$env:LOCALAPPDATA\Programs\sourceorrery"

Invoke-WebRequest "$release/$archive" -OutFile $archive
Invoke-WebRequest "$release/SHA256SUMS" -OutFile SHA256SUMS
$pattern = '^[a-fA-F0-9]{64}\s+\*?' + [regex]::Escape($archive) + '$'
$entry = @(Get-Content SHA256SUMS | Where-Object { $_ -match $pattern })
if ($entry.Count -ne 1) { throw "Missing or ambiguous checksum for $archive" }
$expected = ($entry[0] -split '\s+')[0]
if ((Get-FileHash $archive -Algorithm SHA256).Hash -ne $expected) {
    throw "Checksum mismatch; do not extract this download"
}

Expand-Archive $archive -DestinationPath $dir -Force
[Environment]::SetEnvironmentVariable("Path", "$([Environment]::GetEnvironmentVariable('Path', 'User'));$dir", "User")
```

Open a new terminal and run `sourceorrery --help`.

</TabItem>
<TabItem label="macOS">

Apple silicon shown. On an Intel Mac, use `x86_64-apple-darwin` in the
archive name instead of `aarch64-apple-darwin`.

```bash
set -eu
release=https://github.com/Netizine/sourceorrery/releases/download/v0.1.4
archive=sourceorrery-0.1.4-aarch64-apple-darwin

curl -fLO "$release/$archive.tar.gz"
curl -fLO "$release/SHA256SUMS"
awk -v file="$archive.tar.gz" '$2 == file { print }' SHA256SUMS > "$archive.sha256"
test -s "$archive.sha256"
shasum -a 256 -c "$archive.sha256"

tar xzf "$archive.tar.gz"
sudo mkdir -p /usr/local/bin
sudo install "$archive/sourceorrery" /usr/local/bin/
sourceorrery --help
```

The binaries are not signed or notarised yet, so macOS may block a
browser-downloaded binary. Verify the source and checksum before deciding
whether to allow it in your system's security settings.

</TabItem>
<TabItem label="Linux">

x64 shown. On arm64, use `aarch64-unknown-linux-gnu` in the archive name
instead of `x86_64-unknown-linux-gnu`. The builds are for glibc-based
distributions.

```bash
set -eu
release=https://github.com/Netizine/sourceorrery/releases/download/v0.1.4
archive=sourceorrery-0.1.4-x86_64-unknown-linux-gnu

curl -fLO "$release/$archive.tar.gz"
curl -fLO "$release/SHA256SUMS"
awk -v file="$archive.tar.gz" '$2 == file { print }' SHA256SUMS > "$archive.sha256"
test -s "$archive.sha256"
sha256sum -c "$archive.sha256"

tar xzf "$archive.tar.gz"
sudo install "$archive/sourceorrery" /usr/local/bin/
sourceorrery --help
```

The OS credential store on Linux is Secret Service over D-Bus. On a server
or in a container there is none: use a passphrase protector, as described in
[Headless: WSL, Docker, CI](/guides/headless/).

</TabItem>
</Tabs>

<Aside type="note" title="What a checksum verifies">
These commands stop before extraction if the selected download fails its
checksum. `SHA256SUMS` detects corruption; a checksum hosted beside an
archive does not independently prove who published it. See
[Supply chain](/security/supply-chain/#release-archives) for the remaining gaps.
</Aside>

Shell completions are available with
`sourceorrery completions bash|zsh|fish|powershell|elvish`.

### From source

With Git, Python 3 for version stamping, Rust 1.91.1 or newer, a C compiler,
and on Linux `libdbus-1-dev` and `pkg-config`, build
the release tag from the repository and install the CLI into
`~/.cargo/bin`, which rustup put on your `PATH`:

```bash
git clone https://github.com/Netizine/sourceorrery
cd sourceorrery
git checkout v0.1.4
python scripts/release/set-version.py 0.1.4
cargo install --locked --path crates/sourceorrery-cli
sourceorrery --help
```

Or build without installing: `cargo build --release -p sourceorrery-cli`
leaves the binary at `target/release/sourceorrery` (`sourceorrery.exe` on
Windows). [Building from source](/guides/building-from-source/) covers the
C ABI, every SDK and the test suites.

<Aside>
Headless servers without a credential store can build without OS-keyring
support and use passphrase protectors only:

```bash
cargo build --release -p sourceorrery-cli --no-default-features
```

See [Headless: WSL, Docker, CI](/guides/headless/).
This minimal build also omits the interactive `ui` command; add
`--features ui` if you need it without OS-keyring support.
</Aside>

## Set up a project

With the CLI installed, run the guided first run from your application's
directory:

```bash
sourceorrery setup
```

Six screens take you from a vault with a strong passphrase to a running
program: the vault, a first database password (typed against a strength
meter or generated, never shown), recovery codes and a hint, an
authenticator app as a second factor, the reveal guard, and the manifest.
[First run](/guides/first-run/) walks through each screen and gives the
same steps as commands, which the wizard prints where there is no
terminal. The sections below are the manual path.

## First vault to first run

Run these steps from the directory containing your application. Use a
development credential for the walkthrough.

<Steps>

1. **Create a vault.**

   ```bash
   sourceorrery vault create development
   ```

   The vault is one SQLite file, `vaults/development.sorvault`, under the
   SourceOrrery home directory (`%LOCALAPPDATA%\sourceorrery` on Windows,
   `~/Library/Application Support/sourceorrery` on macOS,
   `~/.local/share/sourceorrery` on Linux). Every value in it is encrypted
   with a vault key that never touches the disk in the clear.

   By default the vault key is protected by the OS credential store (Windows
   Credential Manager, macOS Keychain, Secret Service), so there is nothing
   to type later. Where no store is available, or with
   `--protector passphrase`, you are asked for a passphrase twice. Argon2id
   derives a key that wraps the randomly generated vault key.

2. **Store a secret.**

   ```bash
   sourceorrery secret set database-password --vault development
   ```

   The value is read from a hidden prompt, from stdin when piped, or from a
   file with `--from-file`. There is no `--value` option: arguments leak into
   shell history and process listings. Every `set` creates a new, immutable
   version.

   ```bash
   # From a pipe or a file (one trailing newline from stdin is stripped)
   printf '%s' "$DB_PASSWORD" | sourceorrery secret set database-password --vault development
   sourceorrery secret set tls-key --from-file ./server.key --vault development
   ```

   Names are letters, digits and hyphens, at most
   127 characters.

3. **Inspect without revealing.**

   ```bash
   sourceorrery secret list --vault development
   sourceorrery secret get database-password --vault development
   sourceorrery secret versions database-password --vault development
   ```

   All three print metadata only: version id, status, content type, tags,
   timestamps. Disclosure is a deliberate, audited act:

   ```bash
   sourceorrery secret get database-password --vault development --reveal
   ```

   Add `-o json` to any command for machine-readable output; errors then carry
   a stable [error code](/reference/error-codes/).

4. **Declare what your project needs.**

   ```bash
   sourceorrery init
   ```

   This writes `sourceorrery.toml` next to your code. It is the committed,
   value-free replacement for `.env`:

   ```toml
   [project]
   name = "my-application"
   vault = "development"

   [secrets.database-password]
   required = true
   purpose = "Database authentication"   # documentation only
   ```

   If the project already has a manifest, edit its entries instead of
   running `init --force`, which would replace it.

   A `value = ...` key, or any other unknown key, is a parse error. Keep
   actual credentials out of names, comments and `purpose` fields too:
   these remain plain text. Commit the reviewed manifest, then confirm
   every entry resolves without reading a secret value:

   ```bash
   sourceorrery check
   ```

   The `database-password` row should show `ok`. A missing or inaccessible
   required secret makes the command fail. Metadata checks are audited.

5. **Run your application with its secrets.**

   ```bash
   sourceorrery run -- npm start
   ```

   Replace `npm start` with your application's normal start command. For
   a Python program, for example, use `sourceorrery run -- python app.py`.

   Each declared secret is resolved and placed in the child's environment,
   `database-password` as `DATABASE_PASSWORD` (set `env = "..."` in the
   manifest to choose another name). The parent never prints the values and
   a missing required secret aborts before the child starts.

</Steps>

<Aside type="caution" title="What this does not protect against">
Environment variables are visible to processes with permission to inspect
the child. Code running as your OS user can use the same OS credential
store or a passphrase available to it. SourceOrrery encrypts the values it
stores and audits vault operations, but cannot prevent your application
from logging a value or an agent from reading an existing `.env` file.
The [threat model](/security/threat-model/) explains this boundary.
</Aside>

### Bring an existing project

- [Import a `.env` file](/reference/cli/#import-moving-a-env-file-into-a-vault)

  supported agent. These are workflow instructions, not a security boundary.

## Updating

SourceOrrery deliberately has **no update checks or automatic updater**.
When you choose to update, open the
[latest release](https://github.com/Netizine/sourceorrery/releases/latest)
and read its release notes, then use your original installation method:

- **Cargo:** run `cargo install --locked sourceorrery-cli`. Leaving out
  `--version` selects the latest published version; Cargo replaces an older
  installation. Keep any feature flags you used for a headless build.
- **Release archive:** follow the [download and checksum steps](#from-the-github-release)
  with the new version in place of `0.1.4`. Close the CLI and interactive
  manager before replacing the executable in its existing installation
  directory. On Windows, skip adding that directory to `PATH` again.
- **Source:** follow [From source](#from-source) with the new release tag and
  matching version-stamping argument, then reinstall the CLI. The
  [build guide](/guides/building-from-source/) covers custom builds.

Confirm which version your terminal runs:

```bash
sourceorrery --version
```

Keep your existing vault files and OS credential-store entries; an update
does not require creating a new vault.

**SDKs update separately** through your application's package manager.
For example, use `python -m pip install --upgrade sourceorrery` in your
Python environment, or `npm install @sourceorreryai/sdk@latest` in your
JavaScript/TypeScript project. Update any pinned dependency versions and
regenerate lockfiles through your package manager. Check your
[SDK guide](/sdks/) for native-library requirements, then test your application.

<Aside type="note" title="Compatibility from 0.1.4">
Version **0.1.4** is the backwards-compatibility baseline. Future releases
will continue to support vaults, manifests and public interfaces from
0.1.4 onward.
</Aside>
